# BI-CAR PARTS v47 — SERVER FOUNDATION

Це перший серверний етап BI-CAR PARTS. Він **не замінює одразу весь локальний функціонал v46**, а створює правильну основу для перенесення його в мережу без зберігання бізнес-даних лише у браузері.

## Що вже є в серверній частині

- Node.js + Express.
- PostgreSQL.
- JWT-авторизація працівників.
- Ролі: owner / manager / seller / warehouse.
- Публічний API товарів.
- Гостьове онлайн-замовлення без реєстрації.
- API замовлень для працівників.
- API клієнтів.
- Схема БД для товарів, трьох складів, залишків, рухів товару, клієнтів, авто, замовлень, кас, постачальників, сервісних звернень та журналу аудиту.
- Збереження legacy JSON-резервних копій із локальної версії для подальшої міграції.
- Docker Compose для локального або VPS-запуску.
- Поточний frontend v46 лежить у папці `frontend/` і віддається сервером як головна сторінка.

## Важливо

Поточний `frontend/index.html` усе ще містить стару localStorage-логіку. Тому v47 — це **серверний фундамент**, а не фінальна production-міграція. Наступними проходами треба по черзі перевести товари, замовлення, склади, каси, CRM та фото на API.

## Швидкий запуск через Docker

1. Встановити Docker Desktop або Docker Engine + Compose.
2. Скопіювати `.env.example` у `.env`.
3. Обов’язково змінити `JWT_SECRET`, `ADMIN_PASSWORD` і пароль PostgreSQL.
4. У папці проєкту виконати:

```bash
docker compose up --build
```

5. Відкрити `http://localhost:3000`.
6. Перевірка API: `http://localhost:3000/api/health`.

## Адмін

При першому запуску сервер створює власника з даних `.env`:

- `ADMIN_LOGIN`
- `ADMIN_PASSWORD`

Пароль **ніколи не треба залишати типовим** на сервері в Інтернеті.

## Основні API

- `GET /api/health`
- `POST /api/auth/login`
- `GET /api/auth/me`
- `GET /api/products`
- `GET /api/products/:id`
- `POST /api/products` — owner/manager
- `PUT /api/products/:id` — owner/manager
- `POST /api/orders/guest` — швидке замовлення без реєстрації
- `GET /api/orders` — owner/manager/seller
- `GET /api/orders/:id`
- `PATCH /api/orders/:id/status`
- `GET /api/customers`
- `GET /api/customers/:id`
- `POST /api/admin/snapshots` — збереження JSON backup із локальної системи

## Що робимо наступним

1. Переносимо `products` з localStorage в PostgreSQL та підключаємо поточний каталог до `/api/products`.
2. Переносимо кошик/замовлення в API.
3. Переносимо склади й списання в транзакції PostgreSQL.
4. Переносимо CRM, каси, постачальників і повернення.
5. Фото — у S3/R2/Cloudinary або локальне сховище VPS.
6. Підключаємо LiqPay та API служб доставки тільки через сервер.
7. Після цього прибираємо localStorage як джерело бізнес-даних.

## v54 — Віртуальний асортимент

Додано товари «Під замовлення» без фізичного залишку. Клієнт бачить тільки BI-CAR PARTS, ціну та орієнтовний термін 1–2 дні. Джерело, закупівельна ціна, код і URL постачальника залишаються тільки в адмінці.

Після клієнтського замовлення в адмінці з’являється ручний статус закупівлі:
`Потрібно знайти / закупити → Знайдено → Замовлено → Отримано`.

Автоматичне замовлення постачальнику не використовується.

Для реального масового наповнення каталогу використовуйте дозволений API або офіційний CSV/XML/YML-фід постачальника. Копіювання чужого сайту без дозволу не закладене.


## v55 — Віртуальний каталог тепер видно на сайті

У попередній v54 був доданий механізм «Під замовлення», але не було готових віртуальних позицій у каталозі. Через це візуально нічого нового не було видно.

У v55:
- автоматично додаються 4 **демонстраційні** віртуальні позиції, якщо ще немає жодного віртуального товару;
- на головній є окремий блок **«Під замовлення · 1–2 дні»**;
- у каталозі є фільтр **Усі товари / В наявності / Під замовлення**;
- демо-позиції мають нульовий фізичний залишок, але їх можна замовити;
- джерело закупівлі лишається прихованим від клієнта.

ВАЖЛИВО: це демонстраційні позиції, а не реальні дані стороннього магазину. Для реального наповнення потрібен конкретний дозволений API/CSV/XML/YML-фід постачальника.

**«Під замовлення · 1–2 дні»**.


## v57 — однаковий вигляд товарів для клієнта

Клієнтська частина більше не показує:
- Demo / демо-позначки;
- «віртуальний каталог»;
- «під замовлення»;
- внутрішній статус закупівлі;
- джерело/постачальника;
- спеціальний фільтр віртуальних товарів;
- окремий блок віртуального асортименту;
- попередження в кошику та checkout про спосіб закупівлі.

Усі позиції виглядають як звичайні товари каталогу з кнопкою «У кошик».

Важливо: для товару без фізичного залишку клієнту **не показується неправдиве «В наявності»**. Натомість складський статус просто прихований, а на картці товару використано нейтральне «Доступно для замовлення».

В адмінці внутрішня інформація про відсутність фізичного залишку та необхідність ручної закупівлі збережена.


## v58 — додано віртуальні товари

Додано 6 позицій із внутрішнім типом `virtual`. Для клієнта вони виглядають як звичайні товари каталогу: без написів «віртуальний», «Demo» чи «під замовлення».

В адмінці вони залишаються внутрішньо позначеними як товари без фізичного залишку та після оформлення клієнтського замовлення потрапляють у блок ручної закупівлі.

Позиції додані як тестове наповнення для перевірки механіки. Перед реальним запуском каталог краще підключити до дозволеного API/CSV/XML/YML постачальника та підтягувати актуальні назви, ціни, фото й доступність.


## v59 — двигуни для всіх автомобілів локального каталогу

Тепер кожна марка/модель із поточного `carDb` має заповнений список типів двигунів у:
- пошуку автомобіля на головній;
- підборі автомобіля в каталозі;
- формах, які використовують `specFor()` / `v45EngineOptions()`.

Для популярних моделей додані точніші локальні варіанти, а для решти використовується набір двигунів за маркою/типом виробника.

Це локальна довідкова база для зручного тестування. Вона не є повною заводською базою кодів двигунів. Для точних модифікацій за VIN та каталогу запчастин використовується AutoPartsAPI, коли інтеграція активована.



## v61 — компактна адмін-панель і універсальний пошук

Великі списки в адмін-панелі тепер за замовчуванням згорнуті. Для відкриття використовується кнопка **«Деталі»**, після відкриття — **«Сховати»**.

У великих таблицях/списках додано пошук. Пошук нормалізує пробіли й розділові знаки, тому, наприклад:
- `0 986 494 123`
- `0986494123`
- `0-986-494-123`

знаходять одну й ту саму позицію.

Пошук працює по видимому тексту запису: назва, артикул, бренд, телефон, номер замовлення та інші поля, які є в рядку/картці.

Поведінка автоматично застосовується також до списків, які динамічно оновлюються після зміни статусів.

## v64 — AutoPartsAPI VIN
Реальний ланцюжок: VIN → vehicleId → категорії → запчастини → фото.

Активація: скопіюйте `.env.example` у `.env` і задайте:
```
AUTOPARTSAPI_ENABLED=true
AUTOPARTSAPI_KEY=ВАШ_КЛЮЧ
```
Ключ зберігайте тільки на сервері. У frontend його не вставляйте.

Перевірено на VIN `WDBFA68F42F202731`: vehicleId 9433; категорія Air Filter 100260 повертає 125 позицій.

# v65 — Telegram + Email + Push + онлайн-чат + VIN gate

Додано:

- сповіщення про нове замовлення в Telegram;
- email-сповіщення через SMTP;
- браузерне сповіщення зі звуком, коли адмінка відкрита;
- опційний справжній Web Push через Service Worker + VAPID;
- швидкий онлайн-чат без реєстрації для відвідувача;
- відповіді менеджера в реальному часі в адмін-панелі;
- VIN-підбір змінено: без реєстрації клієнт бачить знайдений автомобіль, а для переходу до категорій і запчастин мусить увійти або зареєструватися.

## Telegram

1. Створити бота через BotFather.
2. Написати боту з потрібного Telegram-акаунта/групи.
3. В `.env`:

```env
TELEGRAM_ENABLED=true
TELEGRAM_BOT_TOKEN=...
TELEGRAM_CHAT_ID=...
```

## Email

Для Gmail рекомендовано App Password:

```env
EMAIL_ENABLED=true
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_SECURE=false
SMTP_USER=bicarparts2026@gmail.com
SMTP_PASS=APP_PASSWORD
NOTIFY_EMAIL_TO=bicarparts2026@gmail.com
```

## Web Push

Згенеруйте ключі:

```bash
npx web-push generate-vapid-keys
```

і заповніть:

```env
WEBPUSH_ENABLED=true
VAPID_PUBLIC_KEY=...
VAPID_PRIVATE_KEY=...
```

Після входу в адмінку натисніть **«Увімкнути push + звук»** і дозвольте сповіщення в браузері.

> Важливо: звук у браузері дозволяється тільки після взаємодії користувача з сайтом — тому є окрема кнопка активації. Web Push у production потребує HTTPS (виняток — localhost).

## Онлайн-чат

Працює через Socket.IO і PostgreSQL. Відвідувачу реєстрація не потрібна. Історія діалогу зберігається на сервері. Адмін відповідає з блоку **«Онлайн-чат»**.

## Серверна адмін-авторизація

Для серверних chat/push-функцій логін/пароль адміна мають збігатися з `ADMIN_LOGIN` / `ADMIN_PASSWORD` у `.env`. Після першого production-запуску обов'язково замініть демо-пароль.

- звук на нове повідомлення після першої взаємодії користувача зі сторінкою;
- якщо жоден менеджер не онлайн, клієнт автоматично отримує повідомлення:

  Повторюється не частіше одного разу на 4 години для одного діалогу.

Додаткові `.env` параметри:

```env
CHAT_MAX_FILE_MB=10

```

Окремого відновлення гостьового діалогу після очищення даних браузера або на іншому пристрої не реалізовано.

- клієнтська реєстрація/вхід для VIN gate перенесені на сервер, пароль зберігається як bcrypt hash;
- публічний endpoint товару більше не повертає закупівельну ціну, джерело та внутрішні поля;
- онлайн-замовлення зберігається в PostgreSQL і після цього запускає Telegram/email/Web Push;
- AutoPartsAPI key залишається тільки на сервері;
- чат, файли, Socket.IO та Web Push працюють за reverse proxy;
- PostgreSQL і Node app не виставляються напряму в Інтернет у production compose;
- додано healthcheck app/db, graceful shutdown, production env validation;
- Caddy автоматично отримує HTTPS-сертифікат для домену;
- VAPID ключі генеруються автоматично першим deploy-скриптом;
- додано скрипт backup PostgreSQL.

## Важливе розмежування

Публічний сайт, VIN/AutoPartsAPI, клієнтська авторизація, чат, online-order persistence та сповіщення вже серверні.
Частина старих внутрішніх ERP-модулів, які історично були зроблені на localStorage (каси/частина CRM/внутрішні документи та деякі службові списки), ще не є повністю багатокористувацькою серверною ERP. Вони не блокують запуск магазину, але для роботи кількох працівників з єдиною базою їх треба надалі переносити на API.

## Один запуск на VPS

На Ubuntu VPS після завантаження папки:

```bash
chmod +x deploy-production.sh
./deploy-production.sh
```

Перший запуск попросить лише домен, логін адміністратора та сильний пароль. PostgreSQL/JWT/VAPID secrets створюються автоматично. Після цього скрипт збирає образи, запускає PostgreSQL + app + Caddy, чекає healthcheck і показує адресу сайту.

Перед запуском DNS A-запис домену має вже вказувати на IP VPS, а порти 80/443 мають бути відкриті.
